## Intent and success

Current project Survey Manager or central/project IT can resolve one existing Area `SURVEY_REVIEWER` obligation by explicitly confirming a replacement Superintendent. Either reuse complete existing exact-Area coverage or establish the missing exact-Area review grant and individual assignment in the same transaction before revoking the departing grant. The replacement retains all existing Areas and their current Superintendent role. No request history or other project role changes. Survey Manager can make the coverage/confirmation decision directly before separately changing a Superintendent's role; IT retains the same resolution mechanism. Successful resolution soft-revokes only the selected departing grant, creates only explicitly confirmed missing replacement coverage, and atomically records reused/new coverage, the confirmer and time. A subsequent role change remains the existing separate Manager command and can still be blocked by other obligations.

The operation never promises that an individual is now removable, that all active work has been reassigned, or that historical requests follow the replacement. Closed projects remain read-only. No Sabine mutation or local preview cutover is part of implementation acceptance.

2. Create a separate resolution-history table and standalone administration area. This isolates the new history but adds another audit source and navigation surface before there is a second supported resolution type. Reject for this slice.

For missing coverage, use one atomic handover (recommended) so coverage creation cannot be left committed while departure resolution fails. A separate assign-coverage command followed by resolution would offer independent preparation, but adds another authority/API and leaves a partially completed handover to recover; defer that alternative.

No permission engine, new role, generalized grant editor, account/invitation subsystem, infrastructure or speculative index is needed. Missing coverage may be created only within this confirmed one-grant handover, for the exact departing Area and an eligible current Superintendent; this is not a standalone Manager grant-creation or general Area editor. Add a purpose-specific authorizer for this resolution only: existing central/project IT as recognized by `assertAccessAdministrator`, OR current active non-subcontractor `SURVEY_MANAGER` membership in this project. Recheck and lock the actual authorizing membership/account evidence. Do not broaden `assertAccessAdministrator` itself: company authority, invitations, recovery and general access administration retain their existing IT boundaries. No Superintendent, Chief, organizational/title-based or other role inherits this power.

## Exact supported scope and coverage

A supported departing grant must be current, tenant/project/subject scoped, `SURVEY_REVIEWER`, and bound to one live top-level Area (`aor_levels.depth=0`, node parent null, not retired). Project-wide/null-scope and non-Area/retired-scope rows remain visible as unsupported obligations. They are not interpreted as project-wide executable coverage or silently deleted. `FIELD_COORDINATOR`, acting grants and all department membership/shared-grant mutation remain unsupported.

For a new resolution, the departing subject must remain an active non-subcontractor project member. IT may inspect inactive subjects for investigation, but this slice refuses their resolution; it does not implement account lifecycle or orphan-account cleanup. Manager discovery, reads and fresh resolutions are limited to active non-subcontractor members already within Team Management's editable personnel population (VIEWER, REQUESTER, SURVEY_SUPERINTENDENT, PARTY_CHIEF, INSTRUMENT_MAN); current Manager/IT/unrelated elevated roles remain outside that personnel scope. This preserves existing role-management boundaries while allowing the owner-requested Superintendent resolution. The departing subject need not retain Superintendent role: the stored obligation itself is the blocker, even if an earlier change left it unusable.

The authorized confirmer selects a replacement **person**, who must be a different active non-subcontractor current `SURVEY_SUPERINTENDENT` in the same tenant/project. No promotion, invitation, company change, title-derived authority or acting grant is inferred. The departing Area is server-derived from the selected grant; clients cannot nominate a different Area.

Two explicit modes are supported:

- `reuse`: replacement already has an unrevoked `SURVEY_REVIEWER` grant and an active individual Area assignment (`department_id IS NULL`) on exactly that Area. Refuse missing coverage; never create it silently.
- `assignAdditional`: with a second explicit confirmation, establish whichever exact-Area grant/individual assignment is missing, retaining any existing qualifying rows and all other Areas. Record explicit coverage intent: TEMPORARY for interim additional coverage or PERMANENT for the later permanent successor. Intent describes this confirmed handover; it creates no different role, permission semantics or expiry behavior. Missing review grant, missing individual assignment, or both are supported. If both already exist, require `reuse` after deliberate reload rather than recording a temporary assignment the command did not create.

The completed handover must have both exact-Area review authority and individual request visibility. A responsibility row alone is insufficient. No ancestor/combined/partial/department/Manager-role/acting coverage substitutes. Use the existing review/visibility semantics for the exact Area and descendants; no new inheritance rule or ticket enumeration. If duplicate qualifying assignments already exist, choose the earliest created/id witness and hold all existing qualifying witnesses; do not normalize or remove them.

New rows use fresh server IDs and current server time, with the actor as grant giver. Revoked/deactivated historical rows are never revived. Existing qualifying coverage is retained with its original provenance; the audit distinguishes reused from newly created rows. An independently eligible IT confirmer may also be replacement; Manager/IT resolution authority alone does not qualify anyone as a replacement Superintendent.

### Meaning and end of temporary coverage

John covers Area1; Jason already covers Area2. The Manager selects Jason with `assignAdditional`. On one successful commit Jason has the missing Area1 assignment/review grant as well as unchanged Area2 coverage, and John's selected Area1 review grant is revoked. If any validation, creation, revocation, audit or ledger step fails, none of that handover commits.

Temporary coverage has no automatic expiry in this slice. Record the explicitly selected TEMPORARY intent in the retained handover evidence and display which coverage rows were added temporarily. Do not relabel reused existing rows. Coverage intent is an audit/UI description, not an acting grant or different permission tier. It remains valid until an authorized, confirmed handover; identifying a successor alone changes no access. Later select Jason's temporary Area1 grant as the departing grant and the eligible permanent Superintendent as replacement, reusing existing complete Area1 coverage or explicitly establishing missing coverage through the same command with PERMANENT intent. New successor coverage must be audited/labeled permanent; do not inherit Jason's temporary intent. There is no automatic scheduler, inferred successor, silent timeout or revocation of Jason's Area2 rights. Existing coverage reused by the handover is not relabeled as newly temporary.

This command does not deactivate John's or Jason's individual Area assignments, move Chief reporting links/crews or demote either person. Those retained obligations can still block role changes. Existing Chief-only unlink is not treated as a Superintendent Area-cleanup authority. A complete Manager-only Superintendent departure and removal of residual individual Area visibility require a separate specified cleanup contract; do not claim the first slice completes that lifecycle. Until then, role guards remain protective and the UI names the remaining obligations plainly.

## Read and command API

Add `/api/projects/[projectId]/survey/protected-obligations` with a small injectable handler and a Tenancy application/repository contract. Responses are private/no-store. UUIDs are canonicalized; duplicate/unknown query fields, malformed JSON, arrays, unknown body keys and invalid bounded pagination are 400.

GET modes:

| Mode | Readers | Inputs and output |
|---|---|---|
| `personnel` | IT or current project Survey Manager | Name/email search, limit10/25/50/100 and nonnegative offset. Bounded existing non-subcontractor project members, identity/current role/active flag, and current protected counts. Manager population is limited to the existing active editable-personnel scope above; only IT may inspect inactive or protected-role subjects. No account creation or generalized project-member directory. |
| `obligations` | IT or current project Survey Manager | Required `userId`, bounded responsibility rows plus full counts/total/pagination, existing acting count and separate department-membership diagnostic count. Return `canResolve` for either authorized confirmer when the subject/supported grant is within their permitted scope and the project is editable. Manager may select eligible replacement evidence and confirm the supported Survey Reviewer resolution. Unsupported acting/department/other responsibility cases retain handoff guidance. Department count is informational; it does not become a new role-removal blocker. |
| `candidates` | IT or current project Survey Manager | Required departing `userId` and `grantId`, bounded name/email search and pagination. Eligible current Superintendent people, including those without coverage of this Area. Return existing exact-Area grant/witness IDs or null, reuse eligibility, and explicit missing-review-grant/missing-individual-assignment flags for the additional-coverage preview. No unbounded all-user/all-grant fetch or candidate promotion. |

Obligation and candidate pages return an opaque32-hex `snapshotToken` (personnel search is discovery, not mutation evidence) generated in the same PostgreSQL statement as its rows/counts. The checksum covers project status/build; scoped Area/node/level state; subject/member/user/company state; scoped responsibility rows including revocations; all eligible replacement users/companies/memberships (including candidates without current coverage), their exact-Area grants and individual assignments; and prior resolution evidence. It is independent of search/pagination and includes the full relevant population, not only the displayed page. Scope it to this tenant/project/departing subject, use deterministic ordering, and keep it separate from the incumbent staffing token. It is a checksum, not a permission credential. The confirmer's current Manager/IT authority is checked independently.

POST requires `userId`, `grantId`, `replacementUserId`, `coverageMode: reuse | assignAdditional`, `expectedSnapshot`, `confirmResolution: true`, and `Idempotency-Key`. `assignAdditional` additionally requires `confirmAdditionalCoverage: true` and `coverageIntent: TEMPORARY | PERMANENT`; reject both fields in `reuse`. Intent is included in the idempotency payload and cannot change during an uncertain retry. Resolve exactly one departing row. The server owns tenant/project/actor, departing Area, coverage IDs, prior state, missing-row decisions, audit and time. Client never supplies grant/assignment IDs to create, role, alternate Area, expiry or audit evidence. This endpoint has no standalone/batch grant creation, grant editor, demotion action or unprotected legacy payload.

Fresh success is200 `{resolved: true, grantId, resolutionEventId, resolvedAt, replacementUserId, replacementGrantId, replacementAssignmentId, createdReviewGrant, createdIndividualAssignment}`. The timestamp/event identify a recorded historical resolution, not a claim that coverage remains valid forever. Errors preserve incumbent conventions:401 invalid/deactivated/stale/revoked session;403 no current role authority;404 wrong tenant/project/subject/grant resource;409 archived, unsupported or changed evidence/ineligible coverage, with `STALE_PROTECTED_OBLIGATIONS` for checksum mismatch. UI reloads after a definitive stale/eligibility conflict; no generic500 replaces an expected domain refusal.

## Transaction, locks and safe retries

Use `withTransaction` and the existing `executeIdempotentHttpMutation` ledger. No broad rewrite of company access, role changes, Area setup or ticket transitions.

1. Authenticate with `requireActiveAuth`; validate paths/body. In the transaction lock the tenant-scoped project `FOR NO KEY UPDATE`. Perform an initial current Manager/IT resolution-authority check before any subject/grant lookup, so an unauthorized actor cannot distinguish guessed grants by eligibility errors. Then refuse archived mutation. This serializes with current role/staffing/project writers while allowing FK key-share checks, preserving the Batch67 deadlock repair.
2. Load scoped historical departing grant identity and the tenant-scoped replacement user identified by the stable payload; a replacement grant need not exist yet. Pre-ledger reads and locks must not filter on active grant, live Area/assignment, current subject membership, replacement role or active replacement identity: those are new-operation eligibility, not permission to retrieve a recorded exact replay. Later Area retirement, assignment deactivation, subject membership removal or replacement role/account loss therefore does not by itself prevent an exact replay by a still-authorized Manager/IT confirmer. Manager-specific live subject-role eligibility also belongs inside the new-operation callback; it must not deny that actor's own recorded replay solely because the subject later moved outside the editable population. Acquire actor/subject/replacement user rows in stable user-id order **FOR SHARE**, then relevant membership rows in stable scope/user order FOR SHARE. Hold and recheck the current authorizing membership (`TENANT_ADMIN`, this project's `PROJECT_ADMIN`, or this project's `SURVEY_MANAGER`), actor active/session state and resource ownership before looking up a replay. The Manager branch also checks/holds the actor's non-subcontractor company eligibility. A Manager from another project has no authority here. If several branches are valid, choose deterministically central IT, then project IT, then Survey Manager, and audit the selected evidence. Central IT does not need operational project membership and gains no request-reading authority. Use shared identity/member locks for validation; do not copy the exclusive actor-account pattern rejected in Batch56.
3. Hold any existing scoped Area node and level FOR SHARE, existing individual Area assignment witnesses FOR SHARE in id order, then historical departing/replacement responsibility rows in stable grant-id order FOR NO KEY UPDATE; tolerate absent/inactive coverage rows until new-operation validation. Re-read after locking. These locks must remain compatible with existing ticket review's shared grant/user/member/company locks. Hold the existing replacement and departing company rows FOR SHARE too; defer non-subcontractor/live-type eligibility to the new-operation callback. Do not lock tickets. Generic Area writers do not take the staffing project lock, so their real row updates must contend on witness/node locks. Absent rows cannot be row-locked: project serialization covers this endpoint and existing participating staffing/role writers, not every generic Area insert. A concurrent same-person/same-Area individual assignment insert may produce duplicate valid witnesses under the incumbent schema; this operation preserves its own confirmed witness and does not claim global uniqueness. Concurrent generic responsibility insertion is fenced by the existing active-grant unique index. Prove rollback, witness retention and absence of deadlocks with actual competing writers; do not add a speculative index or silently change generic setup.
4. Authorize the current Manager/IT confirmer and verify historical resource ownership before the idempotency ledger. A successful exact replay may find the original grant already revoked; it returns only the prior recorded response, performs no write and never resurrects a grant. It does not rerun replacement eligibility as if this were a new operation. Newly archived projects or lost resolution/session authority deny replay. Loss of Manager membership denies unless the same actor independently still has valid central/project IT authority; no prior role, cached UI context or named-team lead substitutes. No replay itself certifies current coverage: the client reloads current obligations after any successful result. Changed payload under the same key retains the incumbent mismatch409.
5. Inside a **new** ledger operation, require a still-active departing grant, current supported subject/scope (including the Manager editable-personnel fence), eligible locked replacement Superintendent, and displayed checksum match. Derive and lock any current exact-Area replacement grant/individual witnesses before validating. `reuse` requires both; `assignAdditional` requires at least one missing row, explicit additional-coverage confirmation and valid selected intent. Create only the missing individual assignment and/or SURVEY_REVIEWER grant, then validate the actual full coverage postcondition. A concurrent responsibility insert must use the existing active-grant unique index; an unexpected uniqueness conflict is409 with full rollback, not silent adoption or retries. Recheck locked eligibility immediately before conditional tenant/project/subject/id/`revoked_at IS NULL` soft-revocation; exactly one affected row is required. A new key against an already resolved grant is409.
6. Insert the resolution audit and, if a grant was created, its existing RESPONSIBILITY_GRANTED event, then the ledger response in the same transaction. Audit/ledger failure rolls back new assignment/grant rows and departing revocation together. All lock-dependent evidence is reconstructed from server reads, not cached UI state.

Actor expiry/logout is rechecked at transaction authorization/replay entry: compare the verified auth.expiresAt with the current time and call requireActiveAuth against the transaction client again, as well as rechecking locked account/session-version and the authorizing Manager/IT membership. Like incumbent routes, an in-flight per-token logout insertion is not globally serialized with every command. Row locks protect account/session-version updates and actual authority memberships used here; no claim is made about all future global lifecycle writers. Validate this exact ordering against two-session tests before calling it race-safe. If a real existing writer forces an incompatible protocol, stop and revise this design rather than adding speculative retries or broad writer refactors.

## Additive retained audit

Proposed migration030 (reconfirm the next number immediately before implementation) adds nullable `resolution_evidence JSONB` to `access_grant_events`. Require object shape when non-null; only `RESPONSIBILITY_REVOKED` and `RESPONSIBILITY_GRANTED` rows may have it. The latter is used only for a grant created by this handover. Existing rows remain null, old company-authority inserts need no new argument, and no historic evidence is fabricated/backfilled. No enum/action expansion or separate event table.

A new resolution inserts one RESPONSIBILITY_REVOKED event with existing tenant/project/subject/actor/action/grant/time columns and version1 evidence containing:

- `kind: SURVEY_REVIEWER_RESOLUTION`, explicit confirmation, `coverageRule: EXACT_AREA`, coverage mode, additional-coverage confirmation when required, and the selected coverage intent only for assignAdditional; derive `temporaryCoverage` from intent (true for TEMPORARY, false for PERMANENT or reuse). A server-generated resolution event ID correlates all newly created coverage evidence.
- Original grant snapshot: id/user/responsibility/Area/granted-by/granted-at, prior revocation null.
- Replacement grant snapshot: id/user/responsibility/Area/granted-by/granted-at/active state, whether reused or created by this resolution, and previous absence where created. Individual assignment evidence likewise records reused/created status and prior absence, so authority creation cannot be mistaken for pre-existing coverage.
- Replacement current role, session version and company id/type; exact reused or newly created individual assignment id/Area/user/created-at; Area id/level/depth/parent/retired state.
- Project status, verified checksum and checked-at/confirmed-at timestamp matching the server-owned operation time. Actor id in the event is the confirmer. Record the authority branch (`TENANT_ADMIN`, `PROJECT_ADMIN` or `PROJECT_SURVEY_MANAGER`) and its tenant/project/user/role membership evidence so Manager decisions are distinguishable from IT decisions. Retain the checked actor account active state and session version, and for the Manager branch the actor company id/type used to establish non-subcontractor eligibility. These are server-read snapshots of the locked authorization evidence; never retain tokens, credentials or session secrets.

If a new replacement grant was created, append a RESPONSIBILITY_GRANTED event for that replacement user/grant with non-null version1 evidence (`kind: SURVEY_REVIEWER_HANDOVER_GRANT`, resolution event ID, original departing grant/Area and complete checked coverage/authority snapshots). The revocation evidence retains any new individual assignment and provenance even when no new grant was needed. No new action enum or project-event category is invented. Acceptance must prove complete linked evidence and atomic failure at either audit insert. Reused grants receive no fabricated grant event.

The inserts are append-only in application behavior; no update/delete route exists for audit rows. Evidence is not a foreign-key substitute for authorization: referenced current rows are checked and locked before revocation, while embedded snapshots preserve proof if they later change. No destructive retention or historic request/ticket-event changes. Add the event payload meaning to CLAUDE's access-administration audit guidance during implementation, preserving ticket-vs-project event boundaries.

Apply the additive migration only to disposable acceptance databases first. No Sabine schema application/cutover is implicitly approved. The old runtime can tolerate the nullable column; a rollback never drops retained evidence or recreates a database. Hosted DB ACL/backup/restore certification remains separate.
