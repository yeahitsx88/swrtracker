## Intent and selected approach

Let the current project Survey Manager finish one remaining individual Superintendent Area obligation without removing coverage prematurely or silently moving people. Example: hand John's Area1 review grant to Jason using the existing Manager/IT handover; deliberately transfer or unlink John's Area1 Chief reporting links using existing Chief staffing; select one exact John Area1 assignment and explicitly confirm its removal against Jason's current complete coverage. Jason keeps Area2 and his existing role. John's role changes only through the separate guarded role form after all obligations are resolved.

The owner selected narrow explicit unlink, with multiple deliberate steps, over a combined Area/reporting handover or leaving departure gated. This specification fills that selected approach's concrete authorization, evidence, API/UI, audit, retry and locking contract. It does not authorize a combined cleanup or new standalone coverage-creation flow.

## Authority and targets

New cleanup reads/command use the existing Manager staffing boundary: actual current project SURVEY_MANAGER membership, active account/session and non-subcontractor company. A user with IT membership is eligible here only if also actually assigned Survey Manager in this project. Existing central/project IT Survey Reviewer handover remains unchanged; this spec does not independently add Superintendent Area unlink to IT-only access or broaden shared access-administrator helpers.

Fresh targets are active non-subcontractor current project SURVEY_SUPERINTENDENT members in a FULL build. Never edit Survey Manager, IT, Chief, IM or unrelated-role assignments through this new action. SETUP and ACTIVE may mutate; ARCHIVED exposes scoped read-only evidence. Inactive/non-Superintendent leftovers require a separate lifecycle contract, not a bypass of current subject eligibility. Do not deactivate accounts or change project/tenant membership.

Select one active aor_assignments UUID owned by that subject in the same tenant/project, user_id present and department_id null, on a live top-level Area (depth0, parent null, not retired). Nested/retired/department/shared assignments remain outside this command. Duplicates are shown as separate rows with their UUIDs; never deduplicate or bulk deactivate. Removing one row can leave duplicate or overlapping individual Area coverage and a role blocker. Current Superintendent Area scope uses individual user assignments; retained department memberships/shared assignments are diagnostics, not an asserted visibility path or role blocker for this role. The UI must say so rather than promising all access is removed.

## Coverage and dependency contract

Choose a distinct active non-subcontractor current project Superintendent with BOTH an active exact-Area SURVEY_REVIEWER responsibility grant and an active exact-Area individual assignment. Bind the exact selected replacement grant/assignment UUIDs to the displayed confirmation and request. Department coverage, ancestor coverage, labels, teams, historical snapshots and a grant without request visibility do not qualify. This command reuses coverage only: no new row, restoration, intent relabeling or automatic successor selection. Use the already-approved handover first if missing coverage must be created.

At fresh commit authorization, no active departing responsibility grant may remain in this Area subtree or with null/project-wide scope. Complete the supported review handover first; unresolved FIELD_COORDINATOR or null-scope responsibility grants require their own contract. Any active departing acting grant also blocks this command because its unvalidated JSON cannot safely be interpreted as unrelated to this Area. Responsibility grants on other exact Areas stay untouched. Department memberships/shared department assignments stay unchanged and do not become new role-removal blockers here. These conservative refusal rules do not resolve or reinterpret protected grants.

No active survey_reporting_links may remain with superintendent_id equal to the departing subject and aor_node_id anywhere in the selected Area subtree. Include current links even when the Chief is inactive, has another role, or the linked node is retired: hiding a link is not resolving it. Descendant traversal remains tenant/project scoped and cycle-safe. Links in other Areas remain unchanged and can still block a later role change.

Resolve each dependent link through existing Manager Chief staffing: deliberately select another covered Superintendent to replace the reporting link, or explicitly unlink that exact link. The Area command moves no Chief or IM. An ineligible/inactive Chief that the existing tool cannot handle remains a specific separate lifecycle blocker. Removing a reporting link can deliberately leave the Chief unlinked; do not automatically assign a replacement or claim this unlink completes operational staffing.

Prior handover audit is useful context but not a mandatory prerequisite: legitimate legacy individual assignments may have no new handover event. Current complete explicitly confirmed replacement coverage, absence of protected dependencies and retained unlink evidence are required regardless. Historical evidence alone never substitutes for current coverage.

## Read and command interface

Extend the existing /api/projects/[projectId]/survey/staffing resource with distinct new modes/action; retain incumbent Chief GET/POST/PATCH contracts verbatim. Keep thin injectable route handlers and focused Tenancy application/repository interfaces. Do not modify old Chief behavior or rename generic link-kind meanings.

New GET modes:
- superintendent-areas, with superintendentId: paginated exact active individual assignment rows, Area state, duplicate/other-visibility warning, Area-subtree protected blocker counts and canUnlink/refusal reason. Retired/nested rows can be diagnosed but not selected for mutation.
- superintendent-area-replacements, with superintendentId and linkId: bounded eligible current Superintendents with complete exact-Area coverage and deterministic selected grant/assignment IDs. Empty results explain that current coverage must first be established through an applicable approved handover or separately authorized administration; never suggest retrying an already-revoked source grant or silently create coverage here.
- superintendent-area-reporting, with superintendentId and linkId: bounded actual dependent reporting rows, Chief identity/eligibility and exact link/Area IDs. Give existing-tool guidance; add no new reporting mutation authority.

Each mode supports name/Area-appropriate search up to200 characters and page sizes10/25/50/100, nonnegative safe-integer offset, deterministic order, complete matching total and snapshotToken. Reject duplicate/unknown query keys, malformed UUIDs, control characters and unsupported mode combinations. Normalize UUIDs once. Responses, including failures, are private,no-store. No ticket list or unbounded personnel fetch.

PATCH input: action="unlink-superintendent-area", superintendentId, linkId, replacementUserId, replacementGrantId, replacementAssignmentId, expectedSnapshot, confirmUnlink=true; require Idempotency-Key. UUIDs must be valid and replacement distinct; checksum is32 lowercase hex. Reject unknown/extra properties, missing confirmation and duplicate/mismatched resource ownership. areaId is derived from the selected assignment, never client-authoritative. Return changed=true, assignmentId, unlinkedAt, unlinkEventId and the actual replacement/witness IDs. Do not return role-change success or assert all visibility was removed.

Use an endpoint namespace distinct from incumbent Chief PATCH keys, scoped by tenant/project/actor. A key reused with changed payload returns409. Original handover and existing staffing clients remain compatible.


## Displayed state, transactions and historical retries

A dedicated cleanup checksum includes the incumbent project staffing state plus responsibility/acting state and the identities/provenance needed for replacement confirmation. Include subject/current Manager membership IDs, role/account/company/session state, project status/build, Area levels/parents/retirement/subtree, relevant individual/shared assignments, reporting rows, current candidate populations, coverage grants/assignments and pertinent retained audit evidence. Source rows, totals and checksum for a read mode come from one SQL statement with actual current Manager authority rechecked in that statement. A separate cached permission check is insufficient.

Define one canonical checksum state keyed by tenant/project/subject, covering all of that subject's assignment Areas and their eligible replacement populations/witnesses; selecting a link does not narrow the hashed state. Search, mode, selected link and page changes do not alter the underlying state token. Keep the original selected-person assignment token through reporting/replacement reads. A mismatch or any definitive409 latches a write block until deliberate reload, including after cancel. Never fetch a new token over old displayed evidence. The new checksum can compose the existing exported staffing CTE with scoped additional evidence; it must not change the old clients' checksum contract.

In one transaction: lock/recheck current editable FULL project, actual Manager authority and scoped historical identities/selected assignment ownership; after lock waits recheck token expiry and requireActiveAuth against the transaction client. Only then consult the endpoint/payload idempotency ledger. For an exact successful historical retry, return the recorded response without current subject/replacement eligibility or active-coverage checks, new audit, deactivation, creation or restored access. Current actor/session/Manager authority/project gates still apply. Retained selected assignment ownership is checked even after its deactivation; historical rows are never hard-deleted by this feature.

For a fresh operation, recheck active subject/replacement Superintendent eligibility and exact selected assignment/Area/witnesses, original displayed checksum, no protected dependencies and no active reporting in the whole Area subtree. Hold the evidence through commit. Soft-deactivate only that one individual assignment using a conditional scoped update that must return exactly one row; zero means409 and full rollback. Recheck/assert complete replacement coverage remains held and write one append-only audit event plus the successful retry result atomically. No-op stale requests are refused rather than creating an unaudited new success.

Lock order follows the protected handover's proven structure: project FOR NO KEY UPDATE first (conflicts with incumbent staffing/role/project writers while allowing audit/grant FK KEY SHARE); sorted shared account/current project membership/company identity locks; exact Area/subtree/level locks; assignment rows in stable UUID order with the selected row FOR NO KEY UPDATE and witness rows held; responsibility/acting/reporting rows held in stable table/UUID order. Verify the actual authorizing membership ID is among held rows after rechecking authority; do not authorize from an unheld newly inserted membership.

The incumbent Chief reporting save/unlink already takes an exclusive project lock, serializing legitimate same-project reporting insert/replace/unlink against the dependency-absence check. Coverage handover also locks this project first. Locks on existing rows alone do not lock an absent dependency: actual two-session tests must prove both winner orders against every existing relevant writer. Account/company/session changes, role changes, Area retirement/moves/level changes, selected/witness deactivation/revocation and reporting insertion must either wait or cause an explicit conflict before new success. Audit FK compatibility and existing cross-project writers must be tested for deadlocks. If a current writer defeats the protocol, stop and revise this proposed contract rather than add retries, advisory/global locks or unrelated lifecycle changes. No global per-token logout serialization or generic assignment uniqueness claim.
