# Reusing a Removed Project Company

The Companies inventory removes project associations while retaining tenant company IDs, company details, employees and history. Registering the same normalized name therefore continues to conflict. The owner-reported `test1` edge case exposed a missing discovery step, rather than authorization to delete or replace retained company records.

Typing a company name now performs debounced, exact normalized-name discovery in the current tenant. Existing Tenant Companies shows matching name, type and Company ID. An associated record says Already on this project; an unassociated record offers **Review Add to Project**, which opens the existing native association pop-up with the original name/type/ID and renewed consent. This uses the existing association POST, preserves the original type and never silently registers a replacement or merges historical duplicate IDs. Case and whitespace variants match the duplicate rule; punctuation remains significant.

Registration waits for lookup and is disabled for a known match. Late lookup responses are ignored, lookup refreshes after company reload, and failed discovery exposes guidance while the server still enforces duplicates. Existing-ID manual association remains supported. A new tenant record created after review still yields a definitive409; deliberate Reload administration and new consent remain required before choosing the existing record. Pending/unknown commands retain their exact body/key/shared owner and cannot dismiss.

The existing authorized project-company GET accepts `companyName`, validates1–200 characters and returns at most100 exact-name matches with association state. Authority precedes resource discovery, and the reader only queries the current tenant. It discloses company metadata, not employees or another tenant's records. POST/DELETE lifecycle barriers, audit and replay contracts remain unchanged; there is no new writer or migration.
