## Shared Command and Notice State

The Project Admin shared layout supplies one `CommandOwner` to personnel/company/settings actions, employee/member creation, Request Policy, subcontractor access/invitations, draft recovery and protected handover. Tenant Accounts supplies one owner to employee/admin creation, tenant disable, review resolution and template creation. Batches have unique owner tokens. A pending, uncertain or stale action holds its owner and blocks competing sibling commands. Mounted hidden editors preserve the exact frozen body and idempotency key; switching task pages does not discard them. Only the action's own unchanged retry or deliberate conflict reload resolves that held command. Definitive 409 responses require reload and renewed consent.

`useAdministrationProgress` permits navigation among sibling task routes while intercepting ordinary links that would leave a held workspace and registering a native before-unload guard. It does not persist commands across an actual page reload. Review/blocker evidence, reasons, consent, stale warnings, loading, errors and completion facts remain inline. Shared ProjectAdministration loading/error/success notices sit outside hidden task areas, so company, grant, whitelist, archive and diagnostics results stay visible on the originating page and after sibling navigation. Request Policy and other editors retain their own visible notices within their task areas.

## Server Ownership and Protections

This authorized restoration crosses presentation and authenticated administration. The new project employee endpoint reuses Identity account creation, coordinates Tenancy membership/independent grants, and appends Audit evidence. Its exclusive tenant lifecycle barrier precedes idempotency/domain work; current account/session and project administrative authority are revalidated before recorded replay. It requires a same-tenant company associated with the target project and commits account, membership, optional independent grant and evidence atomically. Passwords are hashed and excluded from returned/evidence payloads. Public invitation registration remains its separate existing workflow.

Invitations, request configuration and shared templates accept optional idempotency keys for exact retry while retaining existing client compatibility. Their current authority checks precede replay. Invitations also enforce writable/non-preparing project state, store only the invitation record ID in the retry ledger and revalidate that the recorded invitation is still pending before returning its bearer token. No migrations, dependency changes, generalized RBAC or expanded public self-registration are part of this increment.

Archived employee/member/company/setup creation remains restricted with visible read-only explanations. Access removal retains its approved availability; archived status does not erase history. Draft recovery still requires an actual independent Project Admin grant within its established recovery window, and Tenant Admin alone does not gain request-reading or recovery access. Central IT capability does not create operational membership. Lifecycle preparation, company/tenant/project scope, blockers and explicit consent remain authoritative server protections.
