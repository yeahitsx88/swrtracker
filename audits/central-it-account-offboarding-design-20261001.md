## Alternatives and recommended boundary

1. **Recommended: guarded account disable after explicit live-duty resolution.** Small account transition, deterministic refusals and preserved records. Ordinary departing requesters and people with resolved operational duties can be disabled. Some staffing departures remain blocked by separately gated workflows.
2. **Immediate disable regardless of obligations.** Better for urgent access termination, but needs an approved interruption/orphan-recovery policy and worker reconciliation. It is a separate security suspension design, not silently included in this routine offboarding command.
3. **Legacy automatic cascade.** Disable plus draft/Area/roster cleanup would combine several policy decisions, leave newer reporting/team/grant obligations unresolved, and expand scope. Do not select it for this increment.

The recommended contract intentionally changes the older §22 cascade proposal. The owner has now approved preserved drafts/grants and routine duty refusals as policies 2–5. Administrative scope and revised written-design details still require review.

## Administrative authority and tenant scope

The owner selected project-scoped Project Admin authority: “Own projects; if the tenant has a central IT, the disabling flags central IT for review and any tenant wide disabling that may be needed.” This supersedes the earlier alternative requiring Project Admin authority across every affected project before account disablement.

Central IT uses current TENANT_ADMIN authority to disable the tenant account. Project Admin uses current authority in the selected project to disable only that project's access. The project action never sets users.deactivated_at. Other-project access and login remain available after sign-in renewal. Neither branch requires a second administrator's approval. Central IT review is subsequent review, not a prerequisite delaying local disablement.

One person may be Central IT, Project Admin and Survey Manager. Record the actual authorized action scope explicitly: PROJECT_ACCESS or TENANT_ACCOUNT. A person with both administrative roles chooses the intended action and sees its impact; the server validates that branch rather than automatically choosing the broader tenant action. Operational authority still requires their actual Survey Manager role. Survey Manager alone, billing, company/acting authority, titles and teams do not grant admin powers.

Both branches require active account, matching session version, unexpired/unrevoked token, current tenant and project evidence as applicable. Recommended actor-company eligibility remains GC or OWNER_REP for these commands, with company type never granting authority; this detail remains part of written-design review.

Use only the authenticated tenant. Unauthorized actors receive 403 before target disclosure, invalid/revoked/disabled sessions 401, malformed input 400, absent/foreign targets indistinguishable 404. Project Admin must hold authority on the named project and target must have a current or retained membership there. An unrelated project membership or an account with no local membership supplies no authority. No other-project names, blocker details, counts or historical payloads are exposed by the project action. Central IT may inspect the all-project impact set for its own separately confirmed tenant command.

Apply project restrictions to preview, command, target lookup, snapshots, audit, UI and retries. Account-wide disablement remains one users row affecting all tenant projects; another tenant's same-email account remains untouched.

## Project access disablement and Central IT review

This is an additional bounded action, not a synonym for tenant-account deactivation. Preserve the selected project_memberships row and operational role, adding access_disabled_at/access_disabled_by and paired lifecycle validation. Add an independent fixed project_admin_grants assignment so project administration can coexist with Survey Manager. Legacy scalar PROJECT_ADMIN memberships remain supported as admin-only evidence; never infer a lost operational role.

Project disable makes every role/grant held by that subject ineffective in the named project without deleting memberships/grants. All project authority, visibility, staffing, draft recovery, notification recipients and personnel selectors must check effective project-access state. Administrative grants cannot bypass a disabled underlying project membership. A tenant Central IT actor may still use their separate tenant support authority; project disable does not revoke that tenant role. Tenant-account disable is needed to stop tenant authority.

The command preserves users.deactivated_at, tenant membership/company links and every other project's rows. It atomically stamps local disabled metadata, increments users.session_version once, appends a user.project_access_disabled lifecycle event, queues Central IT review when eligible Central IT exists, and completes the retry ledger. The shared JWT uses a global version, so all current sessions require sign-in renewal; this is disclosed in confirmation. After new sign-in, access to other authorized projects works, while the disabled project stays denied. A future per-project session scheme is not introduced here.

Apply approved policies 2–5 to the local action: no self-disable, no automatic cleanup, immutable history, no bundled reactivation, original snapshot/confirmation and exact retries, and current transaction authorization. Resolve live duties and Survey Manager replacement only in the selected project. Local requester-owned drafts/submitted requests remain preserved. Nonlocal duties never block the local action and their details never appear in the local response.

A project-level access-control stamp may also revoke access to an archived project without editing its operational records; this explicit exception to archived operational immutability is proposed for written-design review. A repeat local disable returns changed:false, preserving original metadata, version and event. It does not queue another review. Tenant-account or previously disabled states do not create duplicate transitions.

Confirmation explicitly warns when the subject retains tenant-level Central IT authority: local disable does not prevent separate tenant support access. Central IT review is durable and nonblocking. Proposed account_offboarding_reviews rows carry tenant/project/subject/requesting actor, the local event ID, requested scope PROJECT_ACCESS and reason, creation time, central-recipient IDs and status PENDING/RESOLVED. Create one pending review per local transition when at least one active eligible TENANT_ADMIN exists, including when that administrator is the same person as the local actor. Deduplicate recipients by userId. Use a proposed administrative notification outbox tied to the review/event rather than fabricating a ticket_id in the incumbent ticket-only outbox. Event/review/outbox/ledger and local state commit atomically; notification delivery failure does not undo the completed disable, and delivery retries do not repeat it.

The local response says project access disabled and centralReview=PENDING, or NOT_QUEUED_NO_CENTRAL_IT if there is no eligible Central IT. Absence of Central IT never broadens Project Admin authority or delays local disablement. Show that tenant-wide access remains active. No hidden global shutdown, inferred successor, fabricated tenant administrator or automatic future disablement. In a small company where one person holds all three roles, they can separately review and confirm a tenant action through their Central IT membership. Central IT alone can resolve the review with an explicit recorded reviewed-no-further-action disposition, or link a separately confirmed tenant disable event; a failed global action leaves the review pending.

The tenant lifecycle barrier remains first. Hold/recheck selected project, subject membership/access metadata, Project Admin grant/legacy authority, company/account and duty witnesses. Same-subject project disable and tenant disable serialize: tenant-first makes a later new local action unnecessary (changed:false, ACCOUNT_ALREADY_DISABLED); project-first revokes old sessions, so Central IT renews authentication and reloads the all-project evidence before a new global action. Completed local retry remains historical only after current actor/scope checks.

Before launch, inspect worker behavior for project-disabled people. The existing orphan worker uses users.deactivated_at, so local disable must not pretend to be global deactivation; local live-duty guards prevent stranded execution, and all background subject/recipient authorization must respect local access state.

## Proposed flow and concurrency contract

Central IT's tenant-account preview provides bounded tenant account search, selected identity/company/current disabled state, all-project impact totals, paginated blockers, administrator/Manager continuity evidence and one server-issued snapshot. All preview pages bind to the same snapshot; a changed page latches stale until deliberate reload. The snapshot covers identity/company/session version, tenant/project memberships and statuses, continuity witnesses, live obligations and ticket-duty versions. It excludes unrelated historical payloads so ordinary history reads do not invalidate consent.

Command requires the exact subject ID, displayed snapshot, explicit confirmation, trimmed reason of 10–1000 characters, and Idempotency-Key. Reject unknown mutation fields. Disable remains separate from staffing tools and role forms. Pending or uncertain command freezes subject/body/snapshot/key; retry is the identical request. Any definitive 409 requires explicit reload and new consent. No automatic rebase, bulk operation or automatic cleanup.

The recommended coordination uses the existing tenant row as a lifecycle barrier: every participating tenant writer first holds FOR SHARE on that row; offboarding and authority/session-revoking writers (tenant membership removal/demotion, account/company eligibility changes, session-version bumps and logout) hold FOR UPDATE. Shared writer locks permit normal concurrent writes but block disable until they finish. Choose shared versus exclusive mode before taking the barrier; never upgrade a held shared lock. Acquire the barrier before project/account/membership/token/ticket/ledger locks. Existing project-first code must be integrated into this order before rollout; locking only the new command is ineffective. This is a correctness recommendation with tenant-wide contention cost, to be measured during later implementation acceptance.

Participating writers include protected user mutations, account/tenant/project membership and company changes, staffing/grant/Area/department/team changes, project activation, ticket create/assign/workflow operations, password-reset request/consumption, registration, and background writers that can change blocker evidence. Direct operational SQL must follow the protocol; unrestricted owner SQL cannot be certified by an application gate. Rollout must not mix uncoordinated old writers with enabled offboarding.

Inside the exclusive barrier, check session/logout/expiry and current Central IT authority for TENANT_ACCOUNT, or selected-project Project Admin authority for PROJECT_ACCESS, again after waiting. Re-read target and continuity state. Validate current scope before accessing retry results. For exact completed retries, return historical outcome without applying today's blockers or snapshot; label the result historical, not a new current-state certification. New requests to active targets must match snapshot and pass blockers in the selected action scope. Tenant disable checks every project; project-access disable checks only the named project. Fresh requests to already-disabled targets have no side effects.

For one permitted TENANT_ACCOUNT transition, conditionally update the tenant-scoped active target, insert one account lifecycle event, and store the successful idempotency result through the same DbClient/transaction. Any failure rolls back all three. Same-key collisions serialize; changed payload with same key returns 409. Different keys for one target produce one transition and one changed:false result. Deadlock/timeout/database error returns no success; client retains the original key while outcome is unknown.

Protected mutations take the shared barrier and perform current token, account, role and scope checks inside their transaction after waits. Thus a mutation either finishes before disable commits, or starts/revalidates afterward and is rejected. Recheck time-based expiry before mutation/replay. Logout revocation remains a separate per-token concern: logout uses the exclusive barrier so a revocation cannot commit between the last check and the protected commit. No claim of retroactively retracting an already returned response.

After tenant-account disable commits, every newly authorized protected read/write must reject the target's existing sessions regardless of project, cookie copy or cached browser state. After project-access disable, old sessions are rejected through the global version increment; newly authenticated sessions are also refused access to the disabled project while other authorized projects remain usable. Strengthen the common protected-auth path to include account/version checks; route-level guards remain for transactional revalidation. A read authorized before commit may finish; previously downloaded files cannot be recalled. A login racing disable may issue an old token, but protected access must reject it. Reset request returns the usual generic success with no token for a disabled user; consuming a pre-disable token cannot change disabled credentials. Preserve existing reset history; no reset is a reactivation.

## Recommended interfaces and audit changes after mapping

These are proposals only. No public API, type, schema or code change was made in this assessment.

- Separate resources within the authenticated tenant: Central IT GET /api/accounts, GET/POST /api/accounts/[userId]/offboarding for tenant-account disable; Project Admin GET/POST /api/projects/[projectId]/members/[userId]/offboarding for project-access disable. ## Owner decisions and design gate

The owner approved policies 2–5 and selected project-scoped Project Admin authority with Central IT flagged for subsequent tenant-wide review when present.

1. **Approved policy direction:** either Central IT or Project Admin can act independently; Project Admin disables only access to their own project, while Central IT may separately disable the tenant account. A single person may hold all three administrative/Manager roles. Review routing does not require different people.
2. **Approved policy:** routine disablement follows live-duty resolution in the action's scope; unsupported duties remain blocked, with urgent suspension a separate outcome.
3. **Approved policy:** preserve drafts, memberships/company/history rather than the old automatic cascade; forbid self-disable and loss of the last tenant administrator; require actual Manager replacement.
